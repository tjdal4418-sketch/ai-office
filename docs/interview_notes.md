# 면접용 노트 — AI 오피스 핵심 로직 3가지

> 코드를 몰라도 설명할 수 있게 쓴 노트입니다. 각 항목은 **문제 → 해결 → 쉬운 비유 → 예상 질문** 순서입니다.

## 먼저, 30초 소개

"통합세무팀이 매달 반복하는 급여·기장·부가세·법인세 업무를 AI 직원 5명이 나눠 처리하는 웹앱을 만들었습니다.
핵심 원칙은 **AI는 계산하고 대조해서 초안을 만들 뿐, 최종 확정은 반드시 담당자가 승인**한다는 점입니다.
그래서 세 가지에 공을 들였습니다. 첫째, 승인 없이는 끝나지 않는 작업 흐름. 둘째, 법령 수치를 코드에 박지 않고 근거와 함께 관리·검증하는 방식. 셋째, 세금계산서와 장부를 맞춰 보는 대사 로직입니다."

(데이터는 전부 가상이고 실제 신고용이 아니라는 점을 먼저 말하면 신뢰가 갑니다.)

## 핵심 로직 1. 승인 없이는 끝나지 않는 작업 흐름 (Human-in-the-loop)

### 문제
AI가 만든 세금 계산을 그대로 믿고 신고하면 위험합니다. 틀렸을 때 책임지는 사람은 AI가 아니라 담당자입니다. 그런데 "AI가 알아서 다 해 줍니다"라고만 만들면 아무도 확인하지 않게 됩니다.

### 해결
모든 AI 직원의 작업은 같은 **5단계 상태**를 따라 흐르고, 사람이 승인하는 칸을 건너뛸 수 없게 만들었습니다.

```
대기중 → 일하는중 → 검토필요 → (담당자 승인) → 완료 → 대기중
                  ↘ 오류(사유 표시)         ↘ (반려) → 재작업 또는 오류
```

- 작업 순서는 항상 같습니다: 입력 확인 → 계산·대사 → 이상한 항목 목록 만들기 → 결과 파일 만들기 → **검토필요에서 멈춤**.
- 「검토필요」에서 **담당자 이름을 적고 승인**해야만 「완료」가 됩니다. 반려하면 **사유가 필수**이고, 다시 일하게 하거나 오류로 처리할 수 있습니다.
- 승인·반려 기록(누가, 언제, 어떤 코멘트)은 DB에 남습니다.
- 상태를 바꾸는 통로를 하나(`set_status`)로 통일해서, 화면·활동 로그·DB가 항상 같은 이야기를 합니다.
- AI가 자신 없을 때는 스스로 확정하지 않습니다. 예를 들어 분개 추천은 신뢰도가 낮으면 「확인필요」로 표시하고, 불공제 매입세액은 "후보"만 보여 주고 판단은 담당자에게 맡깁니다.

### 쉬운 비유
**신입사원이 쓴 보고서에 팀장이 결재 도장을 찍는 구조**입니다. 신입(AI)은 빠르게 초안과 "여기가 이상해요" 메모까지 붙여 올리지만, 도장(승인)은 팀장(담당자)만 찍을 수 있고, 도장 찍은 기록이 남습니다.

### 코드 위치
`app/agents/base.py`(공통 작업 순서·상태), `app/core/state.py`(상태 저장), `app/core/review.py`(승인·반려).

### 이렇게 물으면
- **"왜 완전 자동화하지 않았나요?"** 세무 신고는 판단이 들어가고 책임이 사람에게 있습니다. AI가 계산·대조처럼 반복적인 부분을 맡고, 사람은 판단에 시간을 쓰게 하는 것이 목표입니다. 그리고 기록이 남아야 나중에 "누가 확인했는지"를 설명할 수 있습니다.
- **"AI가 틀리면요?"** 틀릴 수 있다는 전제로, 이상 항목을 목록으로 올리고(예: 전월 대비 30% 이상 변동, 최저임금 미달 의심), 자신 없는 건 「확인필요」로 남깁니다.
- **"AI는 어디에 쓰였나요?"** 솔직히 이 버전의 분개 추천은 규칙 기반이고, LLM을 붙일 자리만 만들어 두었습니다. 이 프로젝트의 가치는 "AI를 쓰는 것"보다 "AI를 믿을 수 있게 둘러싸는 구조"에 있다고 생각합니다.

## 핵심 로직 2. 법령 수치를 코드에 박지 않고, 근거와 함께 검증하기

### 문제
세율·보험료율·신고기한은 해마다 바뀝니다. 코드 안에 숫자를 박아 두면 ① 어디서 온 숫자인지 모르고 ② 바뀌었을 때 코드를 뒤져야 하고 ③ 틀려도 아무도 모릅니다.

### 해결
- 모든 수치를 `app/rules/2026/` 의 설정 파일로 빼고, **항목마다 값 + 근거 조문 + 적용연도 + 확인일 + 검증 여부**를 적었습니다. 연도가 바뀌면 `rules/2027/` 폴더를 새로 만들면 됩니다.
- 확신이 없으면 추측하지 않고 `TODO: 확인 필요` 로 두었습니다. 값이 비어 있으면 계산이 오류로 멈춥니다(조용히 틀린 값으로 계산하지 않기).
- 결과 엑셀의 `계산근거` 시트에 쓴 규칙이 그대로 들어가고, 다른 시트의 **계산 셀은 수식으로 그 셀을 참조**합니다. 요율을 고치면 엑셀이 알아서 다시 계산합니다.
- 화면의 「법령 자료실」에서 전 항목의 값·근거·확인 상태를 볼 수 있습니다. 상태는 **확인됨 / 미확인(빨강) / 외부 자료 반입 필요(주황)** 세 가지입니다.

### 검증 결과 (숫자로 말하기)
- 법령 MCP(법령 조회 도구)로 현행 조문을 대조해 **미확인 77개 → 0개**.
- 그 과정에서 **실제로 틀린 값을 찾아 고쳤습니다**:
  1. 근로소득 간이지급명세서는 반기가 아니라 **매월** 제출
  2. 국민연금 상·하한은 연도가 아니라 **7월~다음 해 6월 기간별**로 다름
  3. 신고기한 순연에 **노동절(5/1)** 포함
  4. 사업·기타소득 원천징수는 **10원 미만 버림**
  5. 자녀 세액공제 금액이 **2026.3.1 시행분(20,830 / 45,830 / +33,330)** 기준
- 국세청 간이세액표(647개 구간)를 반입한 뒤, 모든 구간 × 가족 1~11명 × (처음·끝) **14,212건을 원본 엑셀과 전수 대조해 불일치 0건**, 샘플 급여 24명은 원본에서 직접 구간을 찾아 계산한 값과 일치했습니다.

### 쉬운 비유
**요리 레시피에 "소금 한 꼬집"이라고 쓰는 대신, 계량 그램수와 "이 책 몇 쪽에서 가져왔다"는 출처를 적어 두는 것**입니다. 출처가 있으면 나중에 누가 봐도 확인할 수 있고, 확인 못 한 재료는 빨간 표시로 남겨 둡니다.

### 코드 위치
`app/rules/2026/*.yaml`(수치), `app/core/rules.py`(읽기), `app/core/rules_catalog.py`(자료실·확인표), 예: 국민연금 기간별 상·하한은 `app/agents/payroll_calc.py` 의 `pension_limits`.

### 이렇게 물으면
- **"검증을 어떻게 했나요?"** 법령 조회 도구로 조문 원문을 가져와 값과 대조했고, 조문 번호를 항목마다 적었습니다. 법령 도구로 확인할 수 없는 건 따로 분류했습니다. 간이세액표는 국세청 원본 엑셀과 전수 대조했습니다.
- **"그럼 100% 맞나요?"** 아닙니다. 확인한 시점은 2026-11-07이고, **신고서 소득 코드 3개와 공휴일 목록은 외부 자료가 필요해서 아직 반입 전**입니다. 숨기지 않고 화면과 문서에 주황색으로 표시했습니다. 법령이 바뀌면 다시 확인해야 합니다.
- **"왜 굳이 이렇게까지?"** 세무 도구에서 가장 위험한 것은 "그럴듯하지만 틀린 숫자"라고 생각했습니다. 틀린 걸 잡아내는 장치(근거 칸·확인 상태·대조 테스트)가 기능보다 먼저라고 판단했습니다.

## 핵심 로직 3. 세금계산서와 장부를 맞춰 보는 대사 (배트)

### 문제
부가세 신고 전에는 "홈택스의 세금계산서"와 "우리 장부"가 같은지 확인해야 합니다. 건수가 수십~수백 건이면 눈으로 맞추다가 빠뜨립니다. 빠뜨리면 가산세나 세액 오류로 이어집니다.

### 해결
두 목록을 자동으로 짝지어 보고, 결과를 **4가지로 분류**합니다.

1. **1차 매칭**: 사업자번호 + 공급가액 + 작성일이 같으면 짝 → 같은 금액이면 **일치**, 세액만 다르면 **금액차이**
2. **2차 매칭**: 1차에서 못 짝지은 것 중 사업자번호·작성일은 같은데 공급가액만 다르면 **금액차이**
3. 세금계산서에는 있는데 짝 없는 장부 → **장부누락**
4. 장부에는 있는데 짝 없는 세금계산서 → **세금계산서누락** (매출이면 "발행 안 한 것 아닌가", 매입이면 "수취 안 한 것 아닌가" 의심)

여기에 더해 ① 발급기한(작성월 다음 달 10일)을 넘긴 건의 **가산세 위험액**(지연 1%·미발급 2%)과 ② 접대 관련·승용차·면세 관련 같은 **불공제 매입세액 후보**를 표시하고, 후보는 **담당자가 「공제/불공제」로 정하면 신고서 요약이 엑셀 수식으로 바로 다시 계산**됩니다. 날짜만 다른 같은 금액은 일부러 두 건으로 보여 주고 참고 안내를 붙입니다. 합치다가 틀리는 것보다 사람이 보게 하는 편이 안전하기 때문입니다.

### 쉬운 비유
**가계부와 카드 명세서를 줄 맞춰 비교하는 일**입니다. 같은 가게·같은 금액이면 체크, 가계부에만 있으면 "카드 결제를 빠뜨렸나?", 명세서에만 있으면 "가계부에 안 적었나?"를 표시하는 것과 같습니다.

### 코드 위치
`app/agents/vat_calc.py` 의 `reconcile`(대사), `find_keywords`(불공제 후보), `penalty_amount`(가산세 위험).

### 이렇게 물으면
- **"왜 1차·2차로 나눴나요?"** 정확히 같은 건부터 먼저 확정해야, 비슷하게 생긴 건이 엉뚱하게 짝지어지는 걸 막을 수 있습니다. 확실한 것부터 짝짓고 남은 것만 느슨한 기준으로 봅니다.
- **"불공제 여부를 AI가 정하나요?"** 아닙니다. 키워드로 "후보"를 찾아 줄 뿐 판단은 담당자입니다. 이 프로젝트의 원칙 그대로입니다.
- **"테스트는요?"** 계산 로직마다 손으로 계산할 수 있는 작은 예시(월급 300만원 1명 등)로 테스트하고, 엑셀 수식 결과를 파이썬 계산과 셀 단위로 비교합니다. 전체 테스트는 `pytest` 로 돌립니다.

## 덧붙이는 이야기 — 가장 인상 깊었던 점

간이세액표를 반입하기 전, 자녀 세액공제 금액이 **제가 임시로 넣어 둔 값(12,500원 등)과 실제 값(20,830원 등)이 달랐습니다.** 임시값이라고 표시를 해 두었기 때문에 "검증 전"으로 보였고, 실제 표를 받아 바로 고칠 수 있었습니다. 만약 그 값을 그냥 확정값처럼 써 두었다면 모든 급여의 소득세가 틀렸을 겁니다. **"모르면 모른다고 표시한다"는 습관이 오류를 잡아낸 사례**라서 면접에서 꼭 이야기하고 싶습니다.

## 한계도 같이 말하기 (신뢰를 줍니다)

- 월급여 1천만원 초과(계산식 구간), 입·퇴사월 일할계산, 연말정산·퇴직소득은 아직 없습니다.
- 단일 사용자 로컬 앱이라 로그인·권한이 없습니다. 팀 공유는 향후 계획입니다.
- 2027년부터 고용·산재 보수총액신고가 월 보수 신고로 바뀌어서, `rules/2027` 에서 반영해야 합니다.

## 용어 한 줄 풀이

| 용어 | 뜻 |
|---|---|
| 대사(Reconciliation) | 두 자료가 맞는지 줄 맞춰 비교하는 일 |
| 간이세액표 | 월급에서 매달 미리 떼는 소득세를 정해 둔 국세청 표 |
| 원천징수 | 돈을 줄 때 세금을 미리 떼어 대신 내는 것 |
| 시산표 | 모든 계정의 차변·대변 합계가 맞는지 보는 표 |
| 불공제 | 부가세를 낼 때 매입세액으로 빼 주지 않는 것 |
| 기업업무추진비 | 예전 이름은 접대비. 업무와 관련된 접대·선물 등의 비용 |
